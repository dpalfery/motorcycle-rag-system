# Vector Store / SQL Graph Anchor-ID Metadata Contract

**Status:** Archived 2026-08-02
**Date:** 2026-08-01
**Goal:** Replace the implicit, join-by-string overlap between Azure AI Search chunk metadata and the SQL Graph (`dbo.GraphNode`/`dbo.GraphEdge`) with an explicit, minimal set of canonical anchor-ID fields — per-chunk canonical node IDs, parent-document lineage, and a version/content-hash tag — and wire a retrieval-time hop that uses those anchors to cross from a vector hit to its graph neighborhood and back, without duplicating relational data into vector metadata.

---

## 1. Problem / Motivation

**Directive (verbatim, from the user):** the overlap between vector-store metadata and SQL-graph nodes must be strictly limited to canonical anchor IDs — a lightweight bridge, not a data mirror. Duplicating relationships inside vector metadata is an anti-pattern that requires brittle synchronization middleware and breaks down on multi-hop queries. The overlap should carry: (1) canonical node IDs, (2) document lineage (parent document ID + logical path), (3) version/timestamp tags.

**Current state (verified against source, branch `feature/ontology-update`):**

- The vector chunk record (`ChunkIndexingService.ChunkIndexRecord`, the JSONL/Azure AI Search document shape) carries `id, title, content, documentType, category, make, model, year, sourceFile, section, pageNumber, pageRange, primarySection, sectionLevel, sectionHeadings, tableCaption, chunkIndex, tags, contentVector, createdAt, updatedAt`. It carries **no field of any kind that anchors to `dbo.GraphNode`** — no node ID, no `IndexedArtifactId`, no `IngestionJobId`, no content hash.
- The vector document `id` **is already** reused as the primary key of the relational tracking table `dbo.IndexedChunks.ChunkId` (confirmed: `ProcessorArtifactService.ConvertToIndexedChunks` sets `ChunkId = outcome.ChunkId`, and `pdf_processor.py` assigns `"id": f"{upload_id}-pdf-{i}"` to both the vector record and, transitively, the SQL row). This existing anchor is sound and reused throughout this plan as the canonical chunk key — no new ID scheme is introduced.
- `dbo.GraphNode` (`GraphTablesMigration.sql`) has exactly one anchor column: `SourceDocumentId UNIQUEIDENTIFIER NULL`. Its DTO counterpart `GraphNodeDto.SourceDocumentId` is populated from a Python-supplied `sourceDocumentId` string via `Guid.TryParse(...) ?? null` (`GraphEntityIngestionService.MapNodes`) — if the string isn't GUID-shaped the anchor silently becomes `null`. `bike_graph_processor.py` populates it with `upload_id`; `graph_extractor.py` with a caller-supplied `source_document_id`. Neither is guaranteed to be the canonical `IndexedArtifacts.IndexedArtifactId` GUID.
- `dbo.GraphNode`/`GraphEdge` have **no content-hash/version column**. `ManualDocument.SourceContentHash` exists at the document-entity level (`3-Domain/MotorcycleRAG.Domain/Entities/ManualDocument.cs`) but is never propagated to `GraphNode` or to the vector chunk record.
- No code path creates `Type='Chunk'` or `Type='Document'` graph nodes, despite `6-Docs/reference/knowledge-graph-ontology.md` defining both (identity = `IndexedChunks.Id` / `IndexedArtifacts.Id` respectively) with `SOURCED_FROM`/`PART_OF` edges. Root cause: `graph_extractor.extract()` is called **once per document** on a `combined_text` string built by concatenating every chunk's text (`pdf_processor.py`), and internally re-splits that string into LLM batches by a raw character budget (`_split_into_batches`) with no alignment to chunk boundaries — so no code, at any layer, currently knows which chunk produced which extracted entity.
- Retrieval-time hop: `SubAgentToolHandlers` exposes vector tools (`execute_azure_search`, `search_pdf_index`) and graph tools (`search_graph_nodes`, `get_neighbours`, `find_paths`, `get_edges_by_type`) as *independent* LLM tool calls. The vector result payload is `{id, content, score, source}`; the graph result payload is `{id, name, type, description}`. Neither carries a field that could be used to hop into the other system — there is no code-level vector→graph or graph→vector hop today.
- **No anti-pattern found**: neither `MotorcyclePDFProcessor.cs`, `MotorcycleCSVProcessor.cs`, nor `pdf_processor.py` write relational/graph-shaped data (components, relationships, specs) into `DocumentMetadataDto.Tags`/`AdditionalProperties` or `ChunkIndexRecord.tags`. The vector metadata today is under-anchored, not over-mirrored — the "not a data mirror" half of the directive requires no removal/cleanup task.
- `ManualBikeLinker` (creates a `manual-for-bike` `GraphEdge` between a `ManualDocument` GUID and a `BikeModel` GUID) already implements the anchor-bridge pattern the directive asks for, but is **not wired into the ingestion pipeline** — `.LinkAsync(` appears only in its own unit tests and DI registration (`DataPipelineConfiguration.cs`). Confirmed integration point: `IngestionJobService.RunGraphIngestionAsync` already calls `_graphEntityIngestionService.IngestAsync(uploadId, ...)` and has `job.ManualDocumentId` (`Guid?`) and `job.MetadataJson` (parseable via the existing `TryParseMetadata` helper for Make/Model/Year) available at that exact point.
- `IndexedArtifactId` and the resolved `IngestionJobId` are both generated/resolved in .NET **after** `ChunkIndexingService.IndexFromJsonlAsync` has already uploaded documents to Azure AI Search (`ProcessorArtifactService.ProcessSearchChunksAsync`: index first, `Guid.NewGuid()` for the artifact second, job lookup third). Embedding these IDs into the vector record requires resequencing.
- **The Azure AI Search index schema is Pulumi-owned, not runtime-created.** `AzureSearchDocumentService.ExecuteCreateIndexAsync` deliberately throws `NotSupportedException` ("index must be provisioned by Pulumi IaC" — an existing, prior decision). The actual field list lives in `7-Deployment/infrastructure/Program.cs::BuildSearchIndexPayload`. Any new vector-side anchor field requires a code change here (T9); the user has approved this change with an explicit deployment constraint (D6).

## 2. Approved decisions

- **D1 (was Q1).** Full per-chunk canonical-node-ID anchoring is in scope. `graph_extractor.py`'s batching is re-aligned to whole-chunk boundaries (a batch is always an integral set of whole chunks — never a sub-chunk slice), so every extracted node/edge can be attributed to the set of chunk IDs (`sourceChunkIds`) that contributed to the LLM call that produced it. `Chunk` and `Document` graph nodes are materialized **deterministically** (uuid5 from the existing chunk/artifact id — no LLM involvement, same pattern `bike_graph_processor._node_id` already uses), one `Chunk` node per Docling chunk and one `Document` node per artifact, connected by `PART_OF` (Chunk → Document) and `SOURCED_FROM` (extracted entity node → each contributing Chunk) edges, per `6-Docs/reference/knowledge-graph-ontology.md`.
- **D2 (scoping call within Q1, made under Auto Mode).** Full closed-vocabulary enforcement across the *entire* ontology (all ~25 node types / ~30 edge types; ingest quarantine of every unrecognized value; DB `CHECK`/`EDGE CONSTRAINT`) stays **out of scope** — that is the ontology doc's own separately tracked "Enforcement gap" (items 1–3), orthogonal to vector↔graph anchoring, and a materially larger effort. This plan closes only the sub-gap it creates: `Chunk`/`Document` become real, deliberately-emitted node types (not free-form/LLM-invented), and `GraphEntityIngestionService` validates only that (a) a node claiming `Type ∈ {Chunk, Document}` carries the fields that type requires, and (b) `SOURCED_FROM`/`PART_OF` edges connect the endpoint types the ontology specifies. The closeout task (T15) updates the ontology doc to record this narrower closure and leave the rest of the "Enforcement gap" section open and clearly still-attributed to future work.
- **D3 (was Q2).** `ProcessorArtifactService` resolves `IndexedArtifactId` (pre-allocated `Guid.NewGuid()`), the owning `IngestionJobId`, and the owning `ManualDocument.SourceContentHash` **before** calling `ChunkIndexingService.IndexFromJsonlAsync`, and passes all three down so every `ChunkIndexRecord` carries its anchors on the single write. No two-phase merge-patch.
- **D4 (was Q3).** Add `GraphNode.SourceContentHash NVARCHAR(128) NULL` (idempotent migration, mirrors `ManualDocument.SourceContentHash`), populated by `GraphEntityIngestionService` from the same `ManualDocument.SourceContentHash` lookup used for D3 (read once, in .NET, where DB access already exists — not computed or plumbed through Python, which has no DB access).
- **D5 (was Q4).** `ManualBikeLinker.LinkAsync` is wired into `IngestionJobService.RunGraphIngestionAsync`, called immediately after `_graphEntityIngestionService.IngestAsync(...)` succeeds, guarded by `job.ManualDocumentId.HasValue` and successfully-parsed Make/Model/Year from `job.MetadataJson`. Missing/unparseable metadata is a no-op with a log line, consistent with the linker's existing not-found behavior — never a thrown exception.
- **D6 (was Q5) — APPROVED, with a binding constraint on execution.** T9 is a **Pulumi code change** to `7-Deployment/infrastructure/Program.cs` only (`BuildSearchIndexPayload`), adding `indexedArtifactId`, `ingestionJobId`, `sourceContentHash` (`Edm.String`, `filterable`) to every category-partitioned index. It is reviewed like any other code change (normal PR + `code-reviewer` + `security-review`). **Deployment happens solely through the CI/CD pipeline.** No agent — planning or implementing — runs `pulumi up` locally, writes to Azure directly, or pushes to ACR. T9 is unblocked for normal sequencing (§6); the constraint is a deployment-time rule the implementing agent and any CI job must follow, not a pre-implementation approval gate.
- **D7.** Historical backfill is split: (a) `indexedArtifactId`/`ingestionJobId`/`sourceContentHash` for already-indexed chunks are 100% derivable from existing `dbo.IndexedChunks`/`dbo.IndexedArtifacts`/`dbo.ManualDocuments` rows via the already-shared chunk `id` key — this plan's T12 **authors and unit-tests this backfill logic only**; it does **not** execute it against live Azure AI Search (an Azure write, forbidden for any agent under root `AGENTS.md`) — execution is an operator/CI action, run only after T9 is deployed. (b) Historical per-chunk `sourceChunkIds`/`Chunk`-node materialization for *already-processed* documents is **not** backfillable without re-running graph extraction — a data/cost decision for the operator, explicitly out of scope (§8).

## 7. Residual decisions / risks

- **No CI-reachable SQL Server exists anywhere in this repo's test/CI harness (discovered 2026-08-01, during T3 execution).** `SqlGraphRepositoryTests.cs` and every other Persistence test is `FakeDbConnection`/`Mock<ISqlConnectionFactory>`-based; no LocalDB, Testcontainers, or `services:` SQL container exists in any `5-Test/` fixture or `.github/workflows/*.yml`; the sole `(localdb)\MSSQLLocalDB` connection string (`5-Test/MotorcycleRAG.IntegrationTests/appsettings.Test.json`) is unused and Windows-only. It is recorded here as a candidate follow-up plan, not actioned or scheduled by this plan.
- **The tested migration artifact is never executed; the executed artifact was untested (found by the T3 reviewer, 2026-08-01; partially resolved in-plan by T3b).** Verified by grep, not inference: no deployment path runs `4-Persistence/MotorcycleRAG.Persistence/Sql/Migrations/*.sql` — both the CI/CD `sqlcmd` step and the local `DbSetup` CLI execute only `schema.sql`, and `6-Docs/DevOps/database-schema.md` describes the migrations folder as historical. **This is strictly broader than the "no live SQL Server" residual below**, which assumed the static-text proof at least covered the *deployed* change; it did not. T3b closes the coverage half (the `schema.sql` block now has a static text contract). What remains open: the repository still maintains a migrations folder that looks authoritative, is convention-followed by new work, and executes nowhere — an ongoing trap for the next author. Deciding whether to wire it into deployment or retire it is a DevOps/schema-ownership question outside this plan's scope; recorded here as a candidate follow-up.
- **Latent `OBJECT_ID` ordering hazard in the standalone migration file (cleared as non-blocking, recorded because it is conditionally live).** `schema.sql` has no ordering problem — its guard batch runs after the `GO` following the `GraphNode`/`GraphEdge` `CREATE TABLE` batches, so the table always exists by then. The standalone `GraphNodeAnchorColumnsMigration.sql` would have the hazard, but never executes, and is convention-consistent with the existing `IngestionJobStageTrackingMigration.sql`. **It would become a real defect the moment that folder is wired into any deployment path** — which is exactly the follow-up named in the bullet above, so the two must be resolved together.
- **Cleared by review, recorded so they are not re-litigated:** SQL Graph `AS NODE` tables accept ordinary `ALTER TABLE ... ADD` and filtered indexes (the one documented restriction — `ALTER COLUMN` blocked while the column participates in a filtered-index expression — does not apply, since nothing alters `ChunkId` after the index exists), and catalog views behave identically for node tables; `[ChunkId]`/`[SourceContentHash]` naming and `NVARCHAR(128)` ↔ `string?` typing match exactly across T3/T3b/T4/T5; and the anchors present no security surface (static parameterless DDL, no dynamic SQL, no PII).
- **Anchor null-clobber via unmigrated callers (found by `code-reviewer` 2026-08-01; resolved in-plan, not deferred).** T7 shipped as an additive overload whose legacy 3-parameter path passed `Guid.Empty`/`string.Empty`, coerced to explicit `null` on `ChunkIndexRecord`. With no `[JsonIgnore(WhenWritingNull)]` and no custom serializer in `SearchClientFactory.cs`, those nulls serialize as real JSON keys, and Azure AI Search `mergeOrUpload` treats an explicit null as *clear this field*. `ChunkReprocessService` used that legacy overload, so any reprocess after T8 would have silently wiped real anchors off already-indexed documents — no error, no log, no failing test — undermining T9's index fields, T10's hop, and T12's backfill targets. **Resolution is two-layered, both in scope:** (a) T7 now omits null anchors structurally, so an unset anchor can never clear a set one *regardless of caller*; (b) T13/T16 migrate the two remaining callers and T14 deletes the legacy overload so the footgun cannot be re-picked-up. Layer (a) alone would have been sufficient to prevent corruption but would have left reprocessed legacy chunks permanently unanchored; layer (b) alone would have left the next new caller free to reintroduce the bug. **Residual:** any *future* `IChunkIndexingService` caller still has to pass real anchors — T14's single-overload contract is what makes that unmissable, and `code-reviewer` should treat re-introduction of a parameterless/partial overload as a blocking finding.
- **`FindPathsAsync` missing `SourceDocumentId` — ruled IN SCOPE (T17), not deferred.** The absence is pre-existing and independent of this plan in origin, but it is load-bearing *for this plan's stated goal*: §4 T10 requires `HandleFindPathsAsync` to surface `source_document_id`, and the directive's entire premise is document-lineage anchoring. Shipping a `find_paths` hop that returns `null` lineage would make the feature hollow along one of its three retrieval paths. Same reasoning applied to the null-clobber finding: preventing this plan's own feature from being inert is the feature being correct, not scope creep. T17 fixes it alongside the anchor columns, since it is the same CTE edit.
- **`InMemorySearchShimChunkIndexingService` is production code, not scaffolding**, and is not covered by T7's serialization fix because it posts raw JSONL text through verbatim rather than round-tripping `ChunkIndexRecord`. It therefore carries its own Test-contract row (T16, §4) rather than riding on T7's. Flagged because it is easy to mistake for a test double given its name and loopback-only endpoint validation.
- **Artifact-GUID churn on re-ingestion (newly consequential, pre-existing).** `ProcessorArtifactService` mints a fresh `Guid.NewGuid()` for `IndexedArtifactId` on every ingestion, while `dbo.IndexedArtifacts` carries a unique index on `(UploadId, ArtifactType)`. Before this plan, a drifting artifact GUID was invisible; now it is stamped into the vector index, so a re-ingestion (as distinct from a *reprocess*, which correctly reuses the existing row) could leave previously-indexed chunks pointing at an artifact GUID that no longer matches the surviving SQL row. Not introduced by this plan and not fixed by it; recorded because this plan is what makes it observable. Candidate follow-up: have `ProcessorArtifactService` reuse the existing artifact row's ID when `(UploadId, ArtifactType)` already exists, mirroring what `ChunkReprocessService` already does.
