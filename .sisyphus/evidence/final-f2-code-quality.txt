                    CRITICAL ISSUES (Must Fix)

[C-01] SECURITY: Error message leaks internal details to HTTP clients
  File: src/main.py, lines 119, 150, 173
  Code: detail=f"Failed to start PDF processing: {str(e)}"
        detail=f"Failed to start CSV processing: {str(e)}"
        detail=f"Failed to get job status: {str(e)}"
  Risk: Exception messages may contain internal paths, stack traces,
        connection strings, or Azure SDK errors. These are returned
        verbatim in HTTP 500 responses.
  Fix:  Return a generic error message. Log the exception server-side.
        Example: detail="An internal error occurred. Check server logs."

[C-02] SECURITY: Raw exception stored in job status dict, exposed via API
  File: src/processors/pdf_processor.py, line 193
  Code: "error": str(e)
  Risk: The job status endpoint (GET /jobs/{job_id}) returns this dict
        directly. str(e) on Azure SDK exceptions can include account
        URLs, SAS tokens, or connection details.
  Fix:  Store a sanitized/generic error message. Log the full exception
        server-side only.

[C-03] IN-MEMORY JOB STATE: _jobs dict is not persistent or thread-safe
  Files: src/processors/pdf_processor.py (line 19)
         src/processors/csv_processor.py (line 12)
  Code:  _jobs: dict[str, dict] = {}
  Risk:  Module-level dicts are:
         - Lost on process restart (no persistence)
         - NOT safe for multi-worker deployments (each worker has its own dict)
         - Unbounded growth (no eviction/TTL) — memory leak over time
  Impact: HIGH for production use. Acceptable for prototype/dev only.
  Fix:   For production, use Redis or a database for job state. For now,
         document this as a known limitation. At minimum add a size cap
         or TTL eviction.

  File: src/main.py, lines 38-39
  Code: allow_methods=["*"], allow_headers=["*"]
  Risk: While allow_origins is properly restricted via env var, wildcard

  Fix:  allow_methods=["GET", "POST", "OPTIONS"]
        allow_headers=["Content-Type", "Authorization"]

[W-03] sys.path manipulation in main.py
  File: src/main.py, line 13
  Code: sys.path.append(str(Path(__file__).parent / "src"))
  Risk: This is fragile and redundant since main.py IS already in src/.
        The append adds src/src/ to the path, which doesn't exist.
        It works by accident because Python resolves imports from the
        current working directory or the file's directory.
  Fix:  Remove the sys.path.append line. Use proper package structure
        or configure the working directory correctly in the run command.

[W-04] background_tasks parameter unused in FastAPI endpoints
  File: src/main.py, lines 91, 125
  Code: async def process_pdf(request: ..., background_tasks: BackgroundTasks)
  Context: The endpoints accept a BackgroundTasks parameter but don't use
           it — instead they use asyncio.create_task() directly in the
           processors. This is inconsistent.
  Fix:  Either use FastAPI's BackgroundTasks, or remove the unused param.
        asyncio.create_task is fine but the unused param is confusing.

[W-05] Pydantic schema uses deprecated datetime.utcnow
  File: src/models/schemas.py, lines 73, 76, 93, 141, 144
  Code: default_factory=datetime.utcnow
  Risk: datetime.utcnow() is deprecated in Python 3.12+ (returns naive
        datetime). The processors correctly use datetime.now(timezone.utc)
        but the schemas don't match.
  Fix:  Use default_factory=lambda: datetime.now(timezone.utc)

[W-06] GraphExtractor creates a new AsyncClient per call
  File: src/extraction/graph_extractor.py, line 43
  Code: client = ollama.AsyncClient(host=self._host)
  Context: OllamaEmbedder correctly creates the client once in __init__().
           GraphExtractor creates a new client for every extract() call.
  Fix:  Move client creation to __init__() for consistency and to avoid
        repeated connection overhead.

[W-07] .NET IngestionJobService uses null-coalesce throw pattern
  File: IngestionJobService.cs, lines 31-35
  Code: _repository = repository ?? throw new ArgumentNullException(...)
  Context: The project convention elsewhere uses
           ArgumentNullException.ThrowIfNull() (see LocalPipelineService.cs,
           GraphEntityIngestionService.cs). This file is inconsistent.
  Fix:  Use ArgumentNullException.ThrowIfNull(repository) for consistency.

[W-08] GraphEntityIngestionService catches generic Exception twice
  File: GraphEntityIngestionService.cs, lines 49, 67
  Code: catch (Exception ex) { _logger.LogWarning(...); return; }
  Context: Silently swallowing exceptions by logging a warning and
           returning is risky. If blob download fails for a permissions
           error, the caller has no way to know ingestion was skipped.
  Fix:  Consider throwing for non-transient errors (auth failures),
        or at minimum return a result indicating success/failure so
        callers can react.

[W-09] No authentication on Python service endpoints
  File: src/main.py (all endpoints)
